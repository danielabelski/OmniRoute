การบีบอัด OmniRoute ถูกสร้างขึ้นตามสัญญาของเครื่องยนต์ โหมดสามารถรันหนึ่งเอ็นจิ้นได้โดยตรง (`caveman` หรือ `rtk`) หรือไปป์ไลน์แบบสแต็กที่กำหนดซึ่งรันหลายเอ็นจิ้นตามลำดับ

## โหมด

| โหมด         | เส้นทางเครื่องยนต์                                                               | อินพุตที่ตั้งใจไว้                              |
| ------------ | -------------------------------------------------------------------------------- | ----------------------------------------------- |
| `off`        | ไม่มี                                                                            | การเก็บรักษาที่รวดเร็วทันใจ                     |
| `lite`       | ผู้ช่วย Caveman Lite                                                             | การล้างข้อมูลตลอดเวลาที่มีความเสี่ยงต่ำ         |
| `standard`   | มนุษย์ถ้ำ                                                                        | การควบแน่นพร้อมท์ภาษาธรรมชาติ                   |
| `aggressive` | มนุษย์ถ้ำ + history/tool ผู้สรุป                                                 | การสนทนาที่ยาวนาน                               |
| `ultra`      | Caveman + ผู้ช่วยตัดแต่งกิ่ง                                                     | การกู้คืนแบบจำกัดบริบท                          |
| `rtk`        | RTK                                                                              | เอาต์พุตเทอร์มินัล เชลล์ สร้าง ทดสอบ และ git    |
| `omniglyph`  | OmniGlyph                                                                        | บริบทเป็นรูปภาพบนสายผู้ให้บริการดั้งเดิม        |
| `stacked`    | ไปป์ไลน์ ค่าเริ่มต้นของคำขอคือ `session-dedup -> lite` `rtk -> caveman` เลือกใช้ | บันทึกเครื่องมือแบบผสมและร้อยแก้ว ประหยัดสูงสุด |

### โปรไฟล์การบีบอัด OmniGlyph

เอ็นจิ้น `omniglyph` (แพ็คเกจ `omniglyph`, 1.4.0 +) ยอมรับโปรไฟล์ semantic ที่มีชื่อ ตั้งค่าแบบโกลบอลผ่าน `omniglyph.profile` ในการตั้งค่าการบีบอัดหรือต่อขั้นตอนผ่านการกำหนดค่าขั้นตอนของไปป์ไลน์แบบสแต็ก:

| ประวัติโดยย่อ | ขอบเขต                                                                                          |
| ------------- | ----------------------------------------------------------------------------------------------- |
| `aggressive`  | ค่าเริ่มต้น. นโยบายใบเสร็จรับเงินที่เผยแพร่จะวัดระบบภาพ — เอกสารเครื่องมือ และประวัติที่หนาแน่น |
| `balanced`    | คงสถานะดั้งเดิมไว้ ปกป้อง 8 เทิร์นล่าสุด ยุบประวัติที่ปิดเก่ากว่า                               |
| `coding-safe` | คงสิทธิอำนาจ สกีมาของเครื่องมือ และเอาท์พุตเครื่องมือที่ใช้งานจริง ปกป้อง 12 รอบล่าสุด          |
| `passthrough` | เส้นทางที่ไม่มีการเปลี่ยนแปลง เครื่องยนต์ถูกข้าม                                                |

โปรไฟล์คือก** เพดาน ไม่ใช่พื้น** : `mergeCompressionProfileOptions` ในแพ็คเกจปฏิเสธที่จะให้ผู้โทรแทนที่การเปิดเลนที่สูญเสียอีกครั้งที่โปรไฟล์ปิด ดังนั้น `preserveSystemPrompt: false` ต่อขั้นตอนจึงไม่สามารถเปิดใช้งานการบีบอัดระบบอีกครั้งภายใต้ `coding-safe` ได้

วัดจากโค้ดเบสนี้: `coding-safe` และ `balanced` เพิ่ม `minCompressChars` ให้เป็นค่าสูงสุดและคงระบบ สกีมาของเครื่องมือ และผลลัพธ์ของเครื่องมือไว้เดิม ดังนั้นเซสชันที่ยังไม่มีประวัติสะสมแต่หยุดที่ `below_min_chars` และกลไกจะไม่เปลี่ยนแปลงอะไรเลย นั่นคือสาเหตุที่ค่าเริ่มต้นคือ `aggressive` แทนที่จะเป็นโปรไฟล์ที่ปลอดภัยที่สุด

แพ็คเกจแก้ไขขอบเขตโมเดลและโปรไฟล์ของตัวเองจากการกำหนดค่าสภาพแวดล้อม OmniRoute ไม่เคยมอบหมายการตัดสินใจ: อะแดปเตอร์จะปักหมุดโมเดลเกทในขอบเขตที่เข้มงวดที่สุดของแพ็คเกจ ดังนั้นการตั้งค่าสภาพแวดล้อมโฮสต์จึงสามารถจำกัดเฉพาะรายการที่อนุญาตให้แคบลงเท่านั้น และห้ามขยายให้เกินการรับที่วัดได้ของ OmniRoute

## ทะเบียนเครื่องยนต์

รีจิสทรีอาศัยอยู่ใน `open-sse/services/compression/engines/registry.ts` เครื่องยนต์เปิดเผยสัญญาที่ใช้ร่วมกัน:

- `id`: รหัสเอ็นจิ้นที่เสถียร เช่น `caveman` หรือ `rtk`
- `apply(text, config)`: เส้นทางการดำเนินการแบบเดิมที่ใช้โดยไปป์ไลน์แบบเรียงซ้อน
- `compress(input, config)`: พาธการดำเนินการหลักที่ส่งคืนข้อความ + stats
- `getConfigSchema()`: ส่งคืนรูปร่างที่เหมือน JSON-Schema ของการกำหนดค่าที่ถูกต้อง
- `validateConfig(config)`: ส่งคืน `{ valid, errors[] }`

การลงทะเบียนใช้ `registerCompressionEngine(engine)` (หรือ `registerEngine` สำหรับกรณีขั้นสูง) ซึ่งจะเรียก `assertValidEngine()` และ `validateConfig(defaultConfig)` ก่อนที่จะยอมรับ ใช้ `unregisterCompressionEngine(id)` เพื่อลบเอ็นจิ้นขณะรันไทม์

`strategySelector.ts` จะลงทะเบียนเอ็นจิ้นในตัวก่อนที่จะทำการบีบอัด ซึ่งช่วยให้การแสดงตัวอย่าง การบีบอัดรันไทม์ โหมดสแต็ก การทดสอบ และกลไกในอนาคตใช้เส้นทางการดำเนินการเดียวกัน

### การบีบอัดคำอธิบาย MCP (ที่เกี่ยวข้อง)

รีจิสทรีแยกต่างหากจะบีบอัดข้อมูลเมตาคำอธิบายเครื่องมือ MCP ที่ — ระดับรีจิสทรี ดู `open-sse/mcp-server/descriptionCompressor.ts` และ [MCP-SERVER.md](../frameworks/MCP-SERVER.md) โดยนำกฎ Caveman มาใช้ซ้ำ แต่ดำเนินการกับข้อมูลเมตาของเครื่องมือ ไม่ใช่ขอเพย์โหลด

### เครื่องยนต์ในตัวเพิ่มเติม

นอกเหนือจาก Caveman, RTK และ LLMLingua-2 แล้ว รีจีสทรียังจัดส่งเอ็นจิ้น lossless / โครงสร้างพิเศษหลายตัว (ใช้โดยไปป์ไลน์แบบเรียงซ้อน สนามเด็กเล่น และการทดสอบ):

| เครื่องยนต์   | รหัส            | มันทำอะไร                                                                                                                                                                  |
| ------------- | --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CCR           | `ccr`           | Content-Compress-Retrieve (H4): แทนที่บล็อกข้อความขนาดใหญ่ที่ต่อเนื่องกันด้วยการอ้างอิงตามเนื้อหา ดังนั้นบล็อก repeated/large จะถูกส่งเพียงครั้งเดียวและอ้างอิงหลังจากนั้น |
| เฮดรูม        | `headroom`      | SmartCrusher (H3 + N5): การบดอัดแบบตารางแบบไม่สูญเสียของเพย์โหลดอาร์เรย์ JSON ที่เป็นเนื้อเดียวกันให้อยู่ในรูปแบบคอลัมน์ `[N rows]`                                        |
| ไอออไนเซอร์   | `ionizer`       | การสุ่มตัวอย่างแถว Head/middle/tail สำหรับบล็อกที่เป็นเนื้อเดียวกันขนาดใหญ่มาก โดยจัดเก็บส่วนตรงกลางแบบตัดเป็นข้อมูลอ้างอิงที่ระบุถึงเนื้อหา CCR                           |
| เซสชั่น dedup | `session-dedup` | การขจัดข้อมูลซ้ำซ้อนแบบข้ามขั้นตอนที่ระบุถึงเนื้อหา (ได้รับแรงบันดาลใจจาก TokenMizer): ลบข้อความที่เห็นแล้วในรอบก่อนหน้าของเซสชันเดียวกัน                                  |

**คำสั่ง CCR ดึงข้อมูลโปรโตคอล (#8033):** ครั้งแรกที่ CCR แทนที่ ≥ 1 บล็อกในคำขอ เอ็นจิ้นจะเติมข้อความ `system` ที่เป็น idempotent ไว้ข้างหน้า (นำหน้าด้วย `[CCR protocol]` sentinel) สอนผู้เรียกถึงสัญญาเครื่องมือ → : เครื่องหมาย `[CCR retrieve hash=<24hex> chars=N]` หมายถึงอะไร ซึ่งจะต้องคัดลอกแฮชทุกคำ (อักขระฐานสิบหกทั้งหมด 24 ตัว — แฮชที่คัดลอกผิดเป็นสาเหตุที่น่าจะทำให้เกิด "ไม่พบบล็อก" misses) และเครื่องหมาย `[dedup:ref sha=...]` หมายถึง "มองย้อนกลับไปในอดีต" ไม่ใช่ "เรียกเครื่องมือ" บันทึกย่อถูกฉีด** เฉพาะเมื่อ `tools[]` ที่โฆษณาของผู้โทรพิสูจน์ว่าสามารถเข้าถึง `omniroute_ccr_retrieve` ได้จริงเท่านั้น** (`callerSupportsCcrRetrieve()` ใน `open-sse/services/compression/engines/ccr/protocolInstruction.ts`) — ผู้โทรที่เข้ากันได้กับ OpenAI ธรรมดาโดยไม่มีเครื่องมือนั้นจะไม่ได้รับคำสั่งให้โทรหาสิ่งที่ไม่สามารถเข้าถึงได้ การบังคับใช้ค่าเดิมนั้นทำได้โดยการสแกนประวัติข้อความของ Sentinel ก่อนที่จะฉีด ดังนั้นคำขอแบบหลายเทิร์น (ซึ่งเล่นซ้ำข้อความก่อนหน้า) จะไม่ซ้อนบันทึกหนึ่งครั้งต่อเทิร์น

## มนุษย์ถ้ำ

โหมดมนุษย์ถ้ำมุ่งเน้นไปที่การควบแน่นความหมายของร้อยแก้วปกติ:

- เก็บรักษาบล็อกโค้ด, URLs, JSON, เส้นทางและข้อมูลที่มีโครงสร้าง
- ลบฟิลเลอร์ การป้องกันความเสี่ยง บริบทที่ซ้ำ และการใช้ถ้อยคำที่เชื่อมโยงแบบละเอียด
- รองรับชุดกฎไฟล์ที่รับรู้ภาษาใน `open-sse/services/compression/rules/`
- ยังคงใช้งานได้ผ่านโหมด `standard`, `aggressive` และ `ultra` แบบเดิม

พื้นผิวแดชบอร์ดคือ `Dashboard -> Context & Cache -> Caveman`

Caveman upstream รายงานโทเค็นเอาต์พุต `~75%` น้อยลง การประหยัดเอาต์พุตโดยเฉลี่ย `65%` ในการวัดประสิทธิภาพด้วยช่วง `22-87%` และเครื่องมือการบีบอัดอินพุต `~46%` OmniRoute ใช้หมายเลขฝั่งอินพุตของ Caveman เมื่อบันทึกการประหยัด prompt/context แบบซ้อนกัน โหมดเอาท์พุต Caveman ยังคงเป็นคุณลักษณะพฤติกรรมการตอบสนองที่แยกจากกัน

## RTK

โหมด RTK เน้นที่เอาต์พุตคำสั่งและเครื่องมือ:

- ตรวจจับคลาสเอาต์พุตเช่น `git status`, `git branch`, `git diff`, Vitest/Jest/Pytest, การทดสอบ Cargo/Go, TypeScript/Vite/Webpack builds, ESLint, npm audit/installs, บันทึก Docker, เชลล์ `find`/`grep`, การติดตามสแต็ก และบันทึกทั่วไป
- ใช้ตัวกรอง 49 JSON จาก `open-sse/services/compression/engines/rtk/filters/`
- รองรับไปป์ไลน์การประกาศสไตล์ RTK: การแยก ANSI, แทนที่, การลัดวงจรของเอาต์พุตที่ตรงกัน, เส้น strip/keep, การตัดทอนต่อบรรทัด, การตัดทอน head/tail/max-line และทางเลือกสำรองเมื่อว่าง
- รองรับตัวกรองโครงการที่มีรั้วรอบขอบชิดใน `.rtk/filters.json` และตัวกรองส่วนกลางใน `DATA_DIR/rtk/filters.json`
- ตัดลำดับ ANSI สัญญาณรบกวนความคืบหน้า บรรทัดที่ซ้ำกัน และตัวอย่างที่ไม่มีประโยชน์
- รักษาความล้มเหลวที่ดำเนินการได้ คำเตือน ข้อมูลสรุป ไฟล์ที่เปลี่ยนแปลง และบริบทส่วนท้าย
- สามารถเลือกเก็บเอาต์พุตดิบที่แก้ไขแล้วสำหรับ recovery/debugging ผ่านเส้นทางการจัดการที่ได้รับการรับรองความถูกต้องได้

พื้นผิวแดชบอร์ดคือ `Dashboard -> Context & Cache -> RTK`

รายละเอียดการดำเนินการสำหรับตัวกรองแบบกำหนดเอง ความน่าเชื่อถือ ตรวจสอบ และการกู้คืนเอาต์พุตดิบอยู่ใน [`RTK_COMPRESSION.md`](./RTK_COMPRESSION.md)

RTK upstream รายงานการประหยัด `60-90%` สำหรับการบีบอัดคำสั่งเอาต์พุต ตัวอย่าง README แสดงเซสชั่นโค้ด Claude 30 นาทีจากโทเค็น `~118,000` ไปเป็น `~23,900` หรือบันทึก `79.7%`

## LLMLingua-2 (การตัดแต่งกิ่งความหมาย)

โหมด LLMLingua-2 ดำเนินการ** การตัดแต่งโทเค็นความหมาย** บนร้อยแก้วโดยใช้ตัวแยกประเภทโทเค็น ONNX ขนาดเล็ก เสริมกลไก Caveman และ RTK ตามกฎ:

- บีบอัดร้อยแก้วในข้อความที่ไม่ใช่ระบบเท่านั้น บล็อกรหัสรั้วและโครงสร้างอื่น ๆ ที่เก็บรักษาไว้จะไม่มีการเปลี่ยนแปลง
- รันแบ็กเอนด์ `@atjsh/llmlingua-2` (ONNX ผ่าน `@huggingface/transformers`) ในเธรดของผู้ปฏิบัติงาน ดังนั้นการอนุมานแบบจำลองจะไม่บล็อกการวนซ้ำเหตุการณ์คำขอ
- เป็น** วางซ้อนกันได้** (`stackPriority` 35): ในไปป์ไลน์แบบสแต็กมันจะทำงานหลังจากเอ็นจิ้นโครงสร้าง (CCR, session-dedup, headroom, Caveman) แต่ก่อนหน้า `ultra` เนื่องจากการตัดแต่งความหมายมีประสิทธิภาพมากที่สุดกับข้อความที่บีบอัดด้วยโครงสร้างแล้ว — เช่น `rtk -> caveman -> llmlingua`
- **ล้มเหลวในการเปิดเมื่อมีข้อผิดพลาดใด ๆ** (ไม่มี deps ที่เป็นทางเลือก, วางไข่ของผู้ปฏิบัติงาน, โหลดโมเดล, การอนุมาน หรือการหมดเวลา) → ข้อความต้นฉบับจะถูกส่งกลับโดยไม่มีการเปลี่ยนแปลง ไม่มีข้อผิดพลาด

ตำแหน่งเครื่องยนต์: `open-sse/services/compression/engines/llmlingua/`. พื้นผิวแดชบอร์ดคือ `Dashboard -> Context & Cache -> LLMLingua`

### โมเดล

รูปแบบเริ่มต้นคือ**TinyBERT** (`atjsh/llmlingua-2-js-tinybert-meetingbank`, ~ 57 MB, เร็ว) มีความแม่นยำสูงกว่า** BERT-ฐาน** model (`Arcoldd/llmlingua4j-bert-base-onnx`, ~ 710 MB) มีให้ใช้งานผ่านฟิลด์ engine config `model` `@huggingface/transformers` ดาวน์โหลดโมเดลที่เลือกอย่างเกียจคร้านจาก HuggingFace Hub ไปยัง `${DATA_DIR}/models/llmlingua` ในการโทรครั้งแรก (`modelStore.ts`); การแทนที่การกำหนดค่า `modelPath` ชี้ไปที่สำเนาในเครื่องแทน (การติดตั้งแบบออฟไลน์ / แบบช่องว่างอากาศ)

### การพึ่งพาเพิ่มเติมและการติดตั้งตามความต้องการ

เพียร์สแต็กรันไทม์ LLMLingua ที่ตัดได้คือ** ไม่จำเป็น** . สองแพ็คเกจถูกประกาศเป็น `optionalDependencies` ใน `package.json` และเก็บไว้** ภายนอก** โดยการสร้างการผลิต (`scripts/build/prepublish.ts` ไม่ได้รวมกลุ่มไว้):

| บรรจุุภัณฑ์          | เวอร์ชัน (พิน) | หมายเหตุ                               |
| -------------------- | -------------- | -------------------------------------- |
| `@atjsh/llmlingua-2` | `2.0.5`        | แพ็คเกจเข้า; ประกาศให้คนอื่นเป็นเพื่อน |
| `js-tiktoken`        | `^1.0.20`      | โทเค็นไนเซอร์                          |

`@huggingface/transformers` ถูกปักหมุดไว้ที่ `^4.2.0` (แชร์กับเส้นทางการฝังในเครื่องและยังติดตามไปยังบันเดิลแบบสแตนด์อโลนด้วย) `@atjsh/llmlingua-2@2.0.5` เพียร์กับ `"^3.5.2 || ^4.0.0"` ดังนั้นจึงรองรับทั้ง Transformers.js v3 และ v4 ตั้งแต่ 2.0.4 เป็นต้นมา `@atjsh/llmlingua-2` ไม่จำเป็นต้องใช้ `@tensorflow/tfjs` อีกต่อไป ซึ่งจะลบผู้มีส่วนร่วมรายเดียวที่ใหญ่ที่สุด (TensorFlow.js) ออกจากสแต็ก SLM เฉพาะสองแพ็กเกจด้านบนเท่านั้นที่สามารถตัดเพียร์ SLM ได้ `npm install` มาตรฐาน (dev) จะติดตั้งสแต็กทางเลือกโดยอัตโนมัติ เว้นแต่จะมีการละเว้นการขึ้นต่อกันที่เป็นทางเลือก

**ทำไมต้องเป็นตามความต้องการ:** แพ็คเกจที่เผยแพร่โดย npm, บันเดิลแบบสแตนด์อโลน และการจัดส่งอิมเมจ Docker** ปราศจาก** สิ่งเหล่านี้จะช่วยให้ผอมเพรียว เมื่อไม่มีพวกเขา ประตูการพึ่งพาของผู้ปฏิบัติงาน (โพรบแก้ไข `@atjsh/llmlingua-2` ใน `worker.ts`) จะล้มเหลวและกลไก** ความล้มเหลวเปิดขึ้นอย่างเงียบ ๆ** — การเลือก LLMLingua จะกลายเป็น no-op (ข้อความส่งคืนไม่มีการเปลี่ยนแปลง ไม่มีการบันทึกข้อผิดพลาด) หากต้องการเปิดใช้งานในสภาพแวดล้อมที่ถูกตัดแต่ง ให้ติดตั้งสแต็กเสริม:

```bash
# pin to the versions declared in package.json optionalDependencies
npm install @atjsh/llmlingua-2@2.0.5 js-tiktoken
```

การลบ `@tensorflow/tfjs` (2.0.4 +) จะกำจัด ~ 800 MB contributor ที่โดดเด่นก่อนหน้านี้ — รอยเท้าที่เหลือคือ transformers.js + onnxruntime-node runtimes รวมถึงโมเดล TinyBERT (~ 57 MB) ที่ดาวน์โหลดเมื่อใช้งานครั้งแรก (ไม่ใช่ผ่าน npm)

ตามสภาพแวดล้อม:

- **เดฟ / `npm install`** — ติดตั้งโดยอัตโนมัติเว้นแต่คุณจะผ่าน `--omit=optional` (หรือ `--no-optional`) ไม่จำเป็นต้องดำเนินการใดๆ
- **Global npm (`npm i -g omniroute`) / สแตนด์อโลน** — รันคำสั่งติดตั้งด้านบนภายในไดเร็กทอรีแพ็กเกจที่ติดตั้งไว้ หรือติดตั้งใหม่โดยไม่ละเว้น deps เสริม
- **Docker** — เพิ่มคำสั่ง install ในเลเยอร์รูปภาพที่ได้รับ ภาพที่เผยแพร่มีรูปทรงเพรียวบางตามการออกแบบ
- **VPS (PM2)** — ติดตั้งลงใน `node_modules` ของแอป จากนั้นรีสตาร์ทกระบวนการเพื่อให้ผู้ปฏิบัติงานตรวจสอบเกตอีกครั้ง
- **Raw ถัดไปแบบสแตนด์อโลน (`npm run build` → `.build/next/standalone/server.js`)** — การติดตามแบบสแตนด์อโลนจัดส่ง NEITHER ผู้ปฏิบัติงานหรือ deps เสริม ดังนั้นเครื่องยนต์จึงเปิดล้มเหลวโดยไม่แจ้งให้ทราบ `scripts/build/colocate-standalone.mjs` ใช้ทั้งสองอย่างอีกครั้ง (ผู้ปฏิบัติงานสร้าง + option-dep closure ลงในแผนผังแบบสแตนด์อโลน); มันทำงานโดยอัตโนมัติผ่านตะขอ `postbuild` npm หลังจากทุกบิลด์ Idempotent, Fail-soft เมื่อขาด deps

**ตรวจสอบว่าใช้งานได้:** เมื่อเลือก LLMLingua ร้อยแก้วจริงจะย่อขนาดลง (กลไกหยุดการเปิดล้มเหลว) และคำขอแรกจะทริกเกอร์การดาวน์โหลดโมเดลลงใน `${DATA_DIR}/models/llmlingua` ประตูจงใจตรวจสอบเฉพาะ `@atjsh/llmlingua-2` — เพียร์อื่น ๆ นั้นเป็น ESM เท่านั้นและ `require.resolve` พ่นใส่พวกมันแม้ว่าจะมี — อยู่ก็ตาม ดังนั้นผู้ปฏิบัติงานยังคงไม่สามารถเปิดได้หากเพียร์ใด ๆ หายไปอย่างแท้จริงในเวลา `import()`

## ท่อซ้อนกัน

โหมดสแต็กจะรันขั้นตอนไปป์ไลน์ตามลำดับ ค่าเริ่มต้นคือ:

```txt
rtk -> caveman
```

ใช้สิ่งนี้สำหรับเซสชันการเข้ารหัสเอเจนต์ที่พรอมต์รวมเอาต์พุตคำสั่งเข้ากับร้อยแก้วของมนุษย์หรือผู้ช่วย RTK จะลดบันทึกเครื่องมือที่มีเสียงดังก่อน จากนั้น Caveman จะบีบอัดภาษาธรรมชาติที่เหลืออยู่

ขั้นตอนไปป์ไลน์ได้รับการกำหนดค่าด้วย `stackedPipeline` ในการตั้งค่าการบีบอัดหรือผ่านคอมโบการบีบอัด

เมื่อเครื่องยนต์ทั้งสองลดน้ำหนักบรรทุกที่เข้าเกณฑ์เท่ากัน ทบคูณการประหยัด:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

## ตัวกรองแผนผังการเข้าถึง MCP

ตัวกรองอัจฉริยะแผนผังการเข้าถึง MCP คือเลเยอร์การบีบอัดหลังการดำเนินการที่ทำงานบน MCP** ผลลัพธ์ของเครื่องมือ** ไม่ใช่ตามข้อความแจ้งหรือบริบท โดยกำหนดเป้าหมายไปที่แผนผังการช่วยสำหรับการเข้าถึงอย่างละเอียดและเพย์โหลดสแนปช็อตของเบราว์เซอร์ที่ส่งคืนโดยเครื่องมือ เช่น Playwright การใช้คอมพิวเตอร์ และเซิร์ฟเวอร์ MCP ที่ทำงานอัตโนมัติของเบราว์เซอร์

### มันทำอะไร

1. **การตัดเสียงรบกวน** — ลบรายการ generic/text ที่ว่างเปล่า (`- generic:`, `- text: ""`)
2. **พี่น้องล้ม.** — เมื่อ ≥ `collapseThreshold` (ค่าเริ่มต้น 30) บรรทัดที่ต่อเนื่องกันเป็นการทำซ้ำเชิงโครงสร้าง ให้ยุบลงในบรรทัด `collapseKeepHead` แรก (ค่าเริ่มต้น 10) + สรุปการนับ + บรรทัด `collapseKeepTail` สุดท้าย (5 เริ่มต้น)
3. **การเก็บรักษาอ้างอิง** — `[ref=eXX]` พุกที่ Playwright/computer-use ต้องการนั้นไม่เคยถูกแตะต้องเลย
4. **การตัดทอนอย่างหนัก** — หากข้อความหลังจากการยุบยังคงเกิน `maxTextChars` (ค่าเริ่มต้น 50,000) ให้ตัดทอนด้วยคำแนะนำการนำทางเพื่อให้ตัวแทนสามารถทำงานต่อไปได้

### ตำแหน่งเครื่องยนต์

```txt
open-sse/services/compression/engines/mcpAccessibility/
  index.ts            ← smartFilterText() entry point
  collapseRepeated.ts ← sibling-collapse algorithm
  constants.ts        ← DEFAULT_MCP_ACCESSIBILITY_CONFIG
```

### การกำหนดค่า

ควบคุมโดย `compression.mcpAccessibility` ในการตั้งค่าส่วนกลาง (การโยกย้าย 056) การกำหนดค่าเริ่มต้น:

```json
{
  "enabled": true,
  "maxTextChars": 50000,
  "collapseThreshold": 30,
  "collapseKeepHead": 10,
  "collapseKeepTail": 5,
  "minLengthToProcess": 2000
}
```

ตัวกรองจะใช้เฉพาะกับเพย์โหลดผลลัพธ์ของเครื่องมือซึ่งมี `type` เป็น `"text"` และมีความยาวเกิน `minLengthToProcess` เท่านั้น ไม่ส่งผลกระทบต่อการบีบอัดทันทีหรือเพย์โหลดคำขอ

### คาดว่าจะประหยัดได้

60–80% จากผลลัพธ์ของเครื่องมือสแนปชอตของเบราว์เซอร์ ขึ้นอยู่กับความซับซ้อนของหน้า อัลกอริธึมการยุบคือ O(n) ในการนับบรรทัดและเพิ่มเวลาแฝงเล็กน้อย

### ตัวกรองนี้เทียบกับเครื่องยนต์บีบอัดด้านบน

| ด้าน          | มนุษย์ถ้ำ / RTK / ซ้อนกัน | ตัวกรองการเข้าถึง MCP                  |
| ------------- | ------------------------- | -------------------------------------- |
| เป้า          | ขอคำแนะนำ/บริบท           | ผลลัพธ์ของเครื่องมือ MCP               |
| สิ่งกระตุ้น   | การตั้งค่าโหมดการบีบอัด   | `compression.mcpAccessibility.enabled` |
| ขอบเขต        | ข้อความ SSE ทั้งหมด       | ผลลัพธ์ของเครื่องมือเท่านั้น           |
| อ้างอิงจุดยึด | N/A                       | เก็บรักษาไว้โดยไม่มีเงื่อนไข           |

พื้นผิวแดชบอร์ด: `Dashboard -> Context & Cache -> Compression Combos`.

## ข้อกำหนดเบื้องต้น / คู่มือผู้ปฏิบัติงาน (CCR & session-dedup)

CCR (`ccr`) และ `session-dedup` แทนที่หรือลบข้อความแล้วปล่อย a** เครื่องหมาย** ด้านหลัง. ส่วนนี้เป็นข้อมูลอ้างอิงของโอเปอเรเตอร์สำหรับการต่อสายไคลเอ็นต์ การอ่านเครื่องหมายสองตัว และการเรียกข้อมูลหรือการวินิจฉัยเนื้อหาที่ถูกแก้ไข กลไกของเครื่องยนต์แต่ละชนิดได้กล่าวถึงไว้ข้างต้น นี่คือเลเยอร์ "ฉันจะเรียกใช้มันได้อย่างไร"

### การคมนาคมและจุดสิ้นสุด

เซิร์ฟเวอร์ MCP ที่แสดงเครื่องมือ CCR สามารถเข้าถึงได้สามวิธี URL ฐานเริ่มต้นคือ `http://localhost:20128` (`OMNIROUTE_BASE_URL`):

| ขนส่ง                           | URL / คำสั่ง                            | หมายเหตุ                                                                                                                        |
| ------------------------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| HTTP แบบสตรีมได้ (ลูกค้า แนะนำ) | `http://localhost:20128/api/mcp/stream` | ตำแหน่งข้อมูลไคลเอ็นต์ MCP ปัจจุบันพูดคุยด้วย                                                                                   |
| ซิงเกิลตัน SSE ดั้งเดิม         | `http://localhost:20128/api/mcp/sse`    | การขนส่งซิงเกิลตันรุ่นเก่า มัน** ปิด** เซสชันที่สามารถสตรีมได้ ใช้ไคลเอนต์ `streamable-http` กับ `/api/mcp/stream` ไม่ใช่อันนี้ |
| สตูดิโอ                         | `omniroute --mcp`                       | สำหรับการกำหนดค่า IDE MCP ที่สร้างกระบวนการ ไม่มีแฟล็ก `--dev` `omniroute --mcp` คือจุดเริ่มต้น stdio                           |

### ชั้นที่เก็บข้อมูล (สิ่งที่รอดจากการรีสตาร์ท)

CCR คือก** สองชั้น** จัดเก็บ ไม่ใช่ในหน่วยความจำเท่านั้น:

- **ระดับในหน่วยความจำยอดนิยม** — ต่อบล็อก cap 2 MiB, ต่ออาจารย์ใหญ่ 16 MiB, global 64 MiB รายการเริ่มต้นที่ 24 ชั่วโมง TTL (สูงสุด 7 วัน) การดึงข้อมูล MCP เต็มจากหน่วยความจำถูกจำกัดไว้ที่ 256 KiB; สิ่งใดก็ตามที่ใหญ่กว่านั้นยังคงสามารถเข้าถึงได้ผ่านโหมด ranged / grep
- **ชั้น SQLite ที่ทนทาน** (`ccr_blocks`, `COMPRESSION_CCR_DURABLE_STORE`, เปิดตามค่าเริ่มต้น) — สำรองระดับในหน่วยความจำเพื่อให้บล็อกรอดพ้นจากการขับไล่ LRU การรีสตาร์ท หรือการดึงข้อมูลไปยังอินสแตนซ์อื่น แถวจะเก็บ TTL ของบล็อกไว้ ดังนั้นบล็อกที่ผ่าน TTL ของมันจึงหายไปจากทั้งสองระดับ

ยามสามคนเก็บระดับความทนทานที่ผูกไว้ — บล็อกจะคงอยู่เฉพาะหน่วยความจำเมื่อ:

1. บล็อกจบลงแล้ว** 512 KB** (`MAX_DURABLE_BLOCK_BYTES`);
2. รันไทม์คือรันไทม์บนคลาวด์ (ไม่มีดิสก์ในเครื่อง)
3. `COMPRESSION_CCR_DURABLE_STORE=false`.

ดังนั้น "บล็อกหายไป" จึงไม่ใช่เรื่องราวการรีสตาร์ทแบบครอบคลุม: บล็อก sub-512 KB บนรันไทม์ในเครื่องที่ไม่ใช่บนคลาวด์จะคงอยู่ด้วยการรีสตาร์ทผ่านระดับที่คงทนจนกว่า TTL จะหมด ดู [การอ้างอิงสภาพแวดล้อม](../reference/ENVIRONMENT.md) สำหรับตัวแปร

### เครื่องหมายทั้งสอง

| เครื่องหมาย                           | ความหมาย                                                                                                                                           | สิ่งที่นางแบบควรทำ                                                                                                                                                                        |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `[CCR retrieve hash=<24hex> chars=N]` | บล็อกขนาดใหญ่ถูกจัดเก็บตามเนื้อหา                                                                                                                  | โทร `omniroute_ccr_retrieve` ด้วย** คัดลอกแฮช 24-hex แล้วทุกคำ** เพื่อให้ได้ข้อความต้นฉบับกลับมา                                                                                          |
| `[dedup:ref sha=…]`                   | ข้อความที่ถูกลบ `session-dedup` ได้ส่งไปแล้วในเทิร์นก่อนหน้าของเซสชันเดียวกัน นี่คืออัน** การมองย้อนกลับไปโดยเจตนา** ไม่ใช่การสูญหายหรือข้อผิดพลาด | ทำ** ไม่** เรียกเครื่องมือใดก็ได้แล้วทำ** ไม่** พยายาม "สร้างมันขึ้นมาใหม่" ข้อความที่ปรากฏครั้งแรกคือสำเนาตามรูปแบบบัญญัติ เทิร์นปัจจุบันจะไม่ถูกเขียนใหม่ แต่จะถูกตัดออกในเทิร์นภายหลัง |

การมองย้อนกลับของ `[dedup:ref]` เป็นการตัดสินใจโปรโตคอลโดยเจตนา — โดยไม่มีการสร้างใหม่ก่อนส่ง ถือว่า "ข้อความนี้ถูกพูดถึงไปแล้วในช่วงเช้าของเซสชั่นนี้"

### ข้อกำหนดเบื้องต้นของลูกค้า

- **คีย์ (stdio):** ผู้เรียก stdio ไม่มีข้อมูลระบุตัวตนต่อคำขอ ดังนั้นจึงตรวจสอบสิทธิ์ด้วย `OMNIROUTE_API_KEY` (ตั้งค่าในเซิร์ฟเวอร์ MCP `env`) หากไม่มีสิ่งนี้ ผู้โทรจะไม่เปิดเผยตัวตน และเครื่องมือที่ต้องใช้ตัวการอาจลดประสิทธิภาพลง
- **`tools[]` คือเงื่อนไขเบื้องต้นในการฉีด** คำสั่ง CCR ดึงข้อมูลโปรโตคอล (#8033) ถูกฉีดเข้าไป** เท่านั้น** เมื่อคำขอโฆษณา `tools[]` พิสูจน์ว่าลูกค้าสามารถเข้าถึง `omniroute_ccr_retrieve` ได้จริง การจับคู่คือการจับคู่ส่วนต่อท้ายที่ล้อมรอบด้วยตัวคั่น (`__`, `.`, `/`, `:`) — ไม่เคยมีสตริงย่อยเปล่า — ดังนั้นชื่อเนมสเปซเช่น `mcp__gateway__omniroute_ccr_retrieve` ยังคงนับอยู่ `tools[]` ขาดหรือไม่ตรงกันหมายความว่าคำสั่งถูก _not_ ฉีดเข้าไปตามการออกแบบ
- **`codemode:false` (ไคลเอนต์OpenCode )** OpenCode มีค่าเริ่มต้นเป็น Code Mode ซึ่งโฆษณาเฉพาะเครื่องมือดั้งเดิมกับโมเดลและ** ไม่ได้** วางเครื่องมือ MCP ไว้ในรายการ `tools[]` ดั้งเดิม ตั้งค่า `codemode: false` บนรายการเซิร์ฟเวอร์ MCP เพื่อโฆษณาเครื่องมือ `omniroute_ccr_*` นี่คือก** ลูกค้า** การตั้งค่า ไม่ใช่ OmniRoute ยังไม่ได้รับการฉีดคำสั่ง CCR : OpenCode ตั้งชื่อเครื่องมือ `<server>_<tool>` ดังนั้นเซิร์ฟเวอร์ชื่อ `omniroute` เปิดเผย `omniroute_omniroute_ccr_retrieve` และ `_` ไม่ใช่หนึ่งในตัวคั่นที่ตรงกัน
- **ครูใหญ่.** พื้นที่จัดเก็บและการดึงข้อมูลจะถูกแยกออกจากกันตามหลักการที่ได้รับการรับรองความถูกต้อง (ต่อคีย์ API ) คีย์มองเห็นเฉพาะบล็อกของตัวเองเท่านั้น

### ขอบเขตต่อเครื่องมือ

การบังคับใช้ขอบเขตจะเปิดอยู่เสมอสำหรับผู้เรียก HTTP/SSE ที่มีขอบเขตแคบ เครื่องมือ `omniroute_` CCR ต้องการ:

| เครื่องมือ               | ขอบเขต              |
| ------------------------ | ------------------- |
| `omniroute_ccr_store`    | `write:compression` |
| `omniroute_ccr_delete`   | `write:compression` |
| `omniroute_ccr_retrieve` | `read:compression`  |
| `omniroute_ccr_inspect`  | `read:compression`  |
| `omniroute_ccr_list`     | `read:compression`  |
| `omniroute_ccr_stats`    | `read:compression`  |

ขอบเขตที่ขาดหายไปจะส่งกลับค่า** ผลลัพธ์ข้อผิดพลาดของเครื่องมือ MCP** (`isError: true` ไม่ใช่ HTTP 403 — `403 LOCAL_ONLY` เป็นการตรวจสอบเส้นทางป้องกันลูปแบ็คแยกต่างหาก): `Error: Insufficient MCP scopes for <tool>. Missing: <scope>.` คีย์รีโมตขั้นต่ำสามารถเก็บ `mcp:connect` (อนุญาต `/api/mcp/` เฉพาะในเครื่องเท่านั้น) รวมถึงขอบเขต read/write เฉพาะที่ต้องการ

### ขีดจำกัดการดึงข้อมูลและการแบ่งหน้า

ผลลัพธ์ข้อความของเครื่องมือ MCP ถูกตัดรอบๆ `mcpAccessibility.maxTextChars` (ค่าเริ่มต้น `50000`) การดึงข้อมูล `full` ของบล็อกถูกจำกัดไว้ที่ 256 KiB —** ไม่มีการเรียกค้นแบบเต็มไม่มีขอบเขต** . เมื่อ `chars=N` ของบล็อกมีขนาดใหญ่ ให้เพจมันแทนที่จะดึงทั้งหมด:

- กฎง่ายๆ:**`chars > 40000` → ใช้ `mode`** , ไม่เคยเต็มอิ่ม
- `mode:"grep"` — regex `pattern` จับคู่ทีละบรรทัด มากถึง 1,000 บรรทัดที่ตรงกัน (`unique: true` ลดลงซ้ำ) ถูกที่สุดสำหรับ "ค้นหาหนึ่งบรรทัดที่ฉันต้องการ"
- `mode:"lines"` — ช่วงบรรทัดที่มีดัชนี 1 รายการ; ต้องการทั้ง `start` และ `end`
- `mode:"head"` / `mode:"tail"` — first/last `n` เส้น
- `mode:"stats"` บรรทัด — อักขระ และจำนวนไบต์โดยไม่มีเนื้อหา

ใช้ `mode:"lines"` กับ `start`/`end` เพื่อดำเนินการบล็อกยาวๆ ในหน้าต่างๆ แทนที่จะขอทั้งหมดพร้อมกัน

### การตั้งชื่อเครื่องมือ

ปัจจุบันเครื่องมือดึงข้อมูลมีชื่อว่า `omniroute_ccr_retrieve` (คำนำหน้า `omniroute_` เป็นวิธีการแก้ปัญหาแบบเก่าสำหรับการชนกันของชื่อข้ามเซิร์ฟเวอร์) ชื่อเครื่องมือส่วนต่อท้ายที่มีขอบเขตที่สะอาดกว่าและการแก้ไขสำหรับผลลัพธ์ MCP JSON ที่ถูกตัดทอนกลางสตริงจะถูกติดตามเป็นการติดตามอัปสตรีม หน้านี้บันทึกพฤติกรรมการจัดส่งในปัจจุบันเท่านั้น

### วงจรการใช้งานเซสชัน

เซสชัน Streamable-HTTP ไม่ได้ใช้งานและเซิร์ฟเวอร์จะเก็บเกี่ยว หน้าต่างว่างคือค่าคงที่ `MCP_SESSION_IDLE_MS` (อ้างอิงตามชื่อ ไม่ใช่ค่าฮาร์ดโค้ด ดังนั้นหน้านี้จึงไม่เลื่อนไปเมื่อมีการเปลี่ยนแปลง) อาการของเซสชันที่ไม่ได้ใช้งานคือ HTTP 404 ที่มี `Unknown Mcp-Session-Id` — วิธีแก้ไขคือเชื่อมต่อใหม่หรือรีสตาร์ทเซสชัน** ไม่** เพื่อหมุนปุ่ม เปลี่ยนขอบเขต หรือเปลี่ยนชื่อเครื่องมือ

| `omniroute_compression_combo_stats` | `read:compression`  | อ่านการวิเคราะห์ combo/engine    |

## ขอบเขตและข้อยกเว้น

**การฝังจะไม่ถูกบีบอัด** `open-sse/handlers/embeddings.ts` ไม่เคยเรียกโปรแกรมบีบอัดใด ๆ — เนื้อความ request/response ส่งตรงไปยังตัวดำเนินการโดยไม่มีใครแตะต้อง นี่เป็นโครงสร้างในปัจจุบัน (การฝังและการแชทให้เสร็จสิ้นเป็นตัวจัดการที่ไม่ต่อเนื่องกัน) ไม่ใช่การตรวจสอบรันไทม์ แต่หมายความว่าข้อกังวลเกี่ยวกับการบิดเบือนเวกเตอร์ใน #8034 ไม่มีพื้นผิวที่เปิดเผยในเส้นทางการฝัง

**ตัวกรองการแยก Per-model/endpoint (#8034)** สำหรับการแชทให้เสร็จสิ้น ผู้ดำเนินการสามารถตั้งชื่อรหัสโมเดล / เป้าหมาย `provider/model` ที่ต้องไม่ถูกบีบอัด — ราวกั้นจะมีประโยชน์หากการบีบอัดถูกต่อสายให้ใกล้กับเส้นทางที่ฝังอยู่ติดกันในภายหลัง และโดยทั่วไปจะมีประโยชน์สำหรับโมเดลใดๆ ที่มีพรอมต์แบบไบต์ต่อไบต์ที่แน่นอน (การประเมินค่าที่กำหนด คำนำหน้าที่ไวต่อแคช ฯลฯ)

- ฟิลด์การตั้งค่า: `exclusions?: string[]` บนการกำหนดค่าการบีบอัดทั่วโลก (`GET`/`PUT /api/settings/compression`) ยังคงอยู่ผ่านเนมสเปซการบีบอัด `key_value` ที่มีอยู่ (`src/lib/db/compression.ts`) — ไม่มีตารางใหม่
- แท็บแดชบอร์ด:** แดชบอร์ด → การบีบอัด → ข้อยกเว้น** (`/dashboard/compression/exclusions`).
- ไวยากรณ์รูปแบบ: `*` เป็นไวด์การ์ดเพียงตัวเดียว เมตาอักขระ regex อื่นๆ ทั้งหมดในรูปแบบจะถูก Escape ก่อนที่จะจับคู่ ดังนั้น `gpt-5.6` จะจับคู่สตริงลิเทอรัลเท่านั้น ไม่ใช้ `gpt-5x6` (ปลอดภัย ReDoS มีขอบเขต ไม่มีตัวระบุปริมาณที่ซ้อนกัน) รูปแบบจะจับคู่ตัวพิมพ์เล็กและตัวพิมพ์ `provider/model` กับทั้งรหัสโมเดลเปลือยและคอมโพสิต — `gpt-5-6`, `openai/gpt-5-6` และ `openai/*` ทั้งหมดใช้งานได้ และ `*` เพียงอย่างเดียวจะไม่รวมทุกรุ่น
- การจับคู่: `isCompressionExcluded()` / `normalizeCompressionExclusions()` ใน `open-sse/services/compression/exclusions.ts` `chatCore.ts` ตรวจสอบเป้าหมายที่แยกออกทันทีหลังจากแก้ไขการตั้งค่าการบีบอัด** ก่อนที่เครื่องยนต์ใดๆ จะทำงาน** และปฏิบัติต่อการจับคู่ทุกประการเหมือนกับการบีบอัดที่ถูกปิดใช้งานทั่วโลก — เนื้อความคำขอนั้นพิสูจน์ได้ว่าเป็นไบต์เหมือนกัน การข้ามจะถูกบันทึกผ่าน `writeCompressionSkip(..., "excluded")` เพื่อให้มองเห็นการวิเคราะห์ได้
- ค่าเริ่มต้น (รายการ empty/absent ): เหมือนกับพฤติกรรมของ pre-#8034 — ไม่มีการยกเว้นใดๆ

## ข้อจำกัดที่ทราบ

- **LLMLingua-2 (SLM) ต้องการ deps เสริมที่อยู่ร่วม** ผู้ปฏิบัติงานจะทำงานเฉพาะในรุ่นที่ใช้งานจริงเมื่อเพียร์ `@atjsh/llmlingua-2` + มีตำแหน่งร่วมใน `dist/node_modules` (ดู `scripts/build/colocateOptionals.mjs`, #4286) หากไม่มีพวกเขา เครื่องยนต์จะเปิดทำงานล้มเหลว (ส่งคืนข้อความต้นฉบับ) ความละเอียดของผู้ปฏิบัติงานไม่ขึ้นอยู่กับ `import.meta.url` อีกต่อไป (ตายในบันเดิลแบบสแตนด์อโลน) — จะยึดกับรันไทม์ cwd / `argv[1]`
- **ชุดภาษามนุษย์ถ้ำ `de` / `fr` / `ja` เป็นบางส่วน** พวกเขาจัดส่งกฎ `context` + `filler` + `structural` แต่ไม่มีแพ็ก `dedup` / `ultra` ดังนั้นความเข้ม `ultra` จึงไม่แข็งแกร่งกว่า `full` สำหรับภาษาเหล่านั้น (พวกเขาใช้เฉพาะกฎของตัวเองเท่านั้น — ไม่มีการถอยกลับอย่างเงียบ ๆ สำหรับกฎ `dedup`/`ultra` ของภาษาอังกฤษ ซึ่งจะทำให้ข้อความภาษาต่างประเทศเสียหาย) `en` / `es` / `id` / `pt-BR` เสร็จสมบูรณ์ ยินดีสนับสนุนการมีส่วนร่วมของ `dedup.json` + `ultra.json` สำหรับแพ็กบางส่วน
- **การวัดและส่งข้อมูลทางไกลแบบซ้อนจะแสดงเฉพาะเอ็นจิ้นที่บีบอัดเท่านั้น** ขั้นตอนไปป์ไลน์แบบสแต็กที่เอ็นจิ้นรันแต่ประหยัดได้ 0 % จะส่งคืน `stats:null` ดังนั้นจึงไม่ปรากฏใน `engineBreakdown` — ซึ่งแยกไม่ออกจากขั้นตอนที่ถูกข้าม การแยกความแตกต่างระหว่าง "รัน, 0 %" จาก "ข้าม" จะต้องมีการเปลี่ยนแปลงโมเดลการแยกย่อยและถูกเลื่อนออกไป
