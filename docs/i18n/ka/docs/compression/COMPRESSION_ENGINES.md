OmniRoute შეკუმშვა აგებულია ძრავის კონტრაქტების გარშემო. რეჟიმს შეუძლია აწარმოოს ერთი ძრავა პირდაპირ (`caveman` ან `rtk`) ან დეტერმინისტული დაწყობილი მილსადენი, რომელიც ახორციელებს რამდენიმე ძრავას თანმიმდევრობით.

## რეჟიმები

| რეჟიმი       | ძრავის გზა                                                                                       | განზრახ შეყვანა                                               |
| ------------ | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------- |
| `off`        | არცერთი                                                                                          | ზუსტი სწრაფი შენარჩუნება                                      |
| `lite`       | Caveman Lite დამხმარეები                                                                         | დაბალი რისკის მუდმივი გაწმენდა                                |
| `standard`   | Caveman                                                                                          | ბუნებრივ ენაზე სწრაფი კონდენსაცია                             |
| `aggressive` | Caveman + history/tool შემაჯამებლები                                                             | ხანგრძლივი ჩატის სესიები                                      |
| `ultra`      | Caveman + pruning დამხმარეები                                                                    | კონტექსტის ლიმიტის აღდგენა                                    |
| `rtk`        | RTK                                                                                              | ტერმინალი, ჭურვი, აშენება, ტესტირება და git გამომავალი        |
| `omniglyph`  | OmniGlyph                                                                                        | კონტექსტი-როგორც-სურათი მშობლიური პროვაიდერის სადენზე         |
| `stacked`    | მილსადენი. მოთხოვნის ნაგულისხმევი არის `session-dedup -> lite`. `rtk -> caveman` არის დაშვებული. | შერეული ხელსაწყოების ჟურნალები და პროზა, მაქსიმალური დანაზოგი |

### OmniGlyph შეკუმშვის პროფილები

`omniglyph` ძრავა (პაკეტი `omniglyph`, 1.4.0 +) იღებს დასახელებულ სემანტიკურ პროფილს, რომელიც დაყენებულია გლობალურად `omniglyph.profile` მეშვეობით შეკუმშვის პარამეტრებში ან თითო ნაბიჯზე დაწყობილი მილსადენის საფეხურის კონფიგურაციის მეშვეობით:

| პროფილი       | საზღვარი                                                                                                                  |
| ------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `aggressive`  | ნაგულისხმევი. გამოქვეყნებული ქვითრების პოლიტიკა ზომავდა — სურათების სისტემას, ხელსაწყოების დოკუმენტებს და მკვრივ ისტორიას |
| `balanced`    | ინარჩუნებს ცოცხლად სახელმწიფოს, იცავს ბოლო 8 შემობრუნებას, ანგრევს ძველ დახურულ ისტორიას                                  |
| `coding-safe` | ინარჩუნებს ავტორიტეტს, ხელსაწყოების სქემებს და ხელსაწყოების ცოცხალ გამოშვებას, იცავს ბოლო 12 ბრუნს                        |
| `passthrough` | მარშრუტები ტრანსფორმაციის გარეშე; ძრავა გამოტოვებულია                                                                     |

პროფილი არის ა** ჭერი და არა იატაკი** : `mergeCompressionProfileOptions` პაკეტში უარს ამბობს აბონენტს ნებას აარიდოს ხელახლა გახსნას დაკარგვის ზოლი, რომლის პროფილიც დახურულია, ამიტომ თითო ნაბიჯი `preserveSystemPrompt: false` არ შეუძლია ხელახლა ჩართოს სისტემის შეკუმშვა `coding-safe`.

იზომება ამ კოდის ბაზაზე: `coding-safe` და `balanced` ამაღლებენ `minCompressChars` მაქსიმუმამდე და ინარჩუნებენ სისტემას, ხელსაწყოების სქემებს და ხელსაწყოების შედეგებს, ასე რომ სესია, რომელსაც ჯერ არ დაუგროვდა ისტორია, ჩერდება `below_min_chars` ზე და ძრავა არაფერს გარდაქმნის. ამიტომ ნაგულისხმევი არის `aggressive` და არა ყველაზე უსაფრთხო პროფილი.

პაკეტი წყვეტს საკუთარი მოდელის ფარგლებს და პროფილს მისი გარემოს კონფიგურაციიდან. OmniRoute არასოდეს გადაწყვეტს გადაწყვეტილებას: ადაპტერი ამაგრებს მოდელის კარიბჭეს პაკეტის ყველაზე შემზღუდველ ფარგლებს, ამიტომ მასპინძელი გარემოს პარამეტრებს შეუძლიათ მხოლოდ შეზღუდონ დაშვების სია და არასოდეს გააფართოვონ იგი OmniRoute ის გაზომილი ქვითრების შემდეგ.

## ძრავის რეესტრი

რეესტრი ცხოვრობს `open-sse/services/compression/engines/registry.ts` ში. ძრავები ავლენს საერთო კონტრაქტს:

- `id`: სტაბილური ძრავის ID, როგორიცაა `caveman` ან `rtk`
- `apply(text, config)`: მემკვიდრეობითი შესრულების გზა, რომელსაც იყენებენ დაწყობილი მილსადენები
- `compress(input, config)`: პირველადი შესრულების გზა, რომელიც აბრუნებს ტექსტს + სტატისტიკას
- `getConfigSchema()`: აბრუნებს JSON-სქემის მსგავს ფორმას სწორი კონფიგურაციის
- `validateConfig(config)`: აბრუნებს `{ valid, errors[] }`

რეგისტრაცია იყენებს `registerCompressionEngine(engine)` (ან `registerEngine` მოწინავე შემთხვევებისთვის), რომელიც მიღებამდე უწოდებს `assertValidEngine()` და `validateConfig(defaultConfig)`. გამოიყენეთ `unregisterCompressionEngine(id)` ძრავის ამოსაღებად მუშაობის დროს.

`strategySelector.ts` აღრიცხავს ჩაშენებულ ძრავებს შეკუმშვის დაწყებამდე. ეს საშუალებას აძლევს გადახედვას, გაშვების დროის შეკუმშვას, დაწყობილ რეჟიმს, ტესტებს და მომავალ ძრავებს გამოიყენონ იგივე შესრულების გზა.

### MCP აღწერილობის შეკუმშვა (დაკავშირებული)

ცალკე რეესტრი შეკუმშავს MCP ინსტრუმენტის აღწერილობის მეტამონაცემებს რეესტრის დონეზე — იხილეთ `open-sse/mcp-server/descriptionCompressor.ts` და [MCP-SERVER.md](../frameworks/MCP-SERVER.md). ის ხელახლა იყენებს Caveman-ის წესებს, მაგრამ მუშაობს ხელსაწყოების მეტამონაცემებზე და არ ითხოვს დატვირთვას.

### დამატებითი ჩაშენებული ძრავები

Caveman-ის, RTK და LLMLingua-2 მიღმა, რეესტრი აგზავნის რამდენიმე სპეციალიზებულ უზარმაზარ / სტრუქტურულ ძრავას (გამოიყენება დაწყობილი მილსადენებით, სათამაშო მოედნით და ტესტებით):

| ძრავი           | ID              | რასაც აკეთებს                                                                                                                                                                 |
| --------------- | --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CCR             | `ccr`           | Content-Compress-Retrieve (H4): ცვლის დიდ მომიჯნავე ტექსტურ ბლოკებს შინაარსზე მიმართული მითითებებით, ამიტომ repeated/large ბლოკები იგზავნება ერთხელ და შემდგომში მითითებულია. |
| სათავე ოთახი    | `headroom`      | SmartCrusher (H3 + N5): ჰომოგენური JSON მასივის დატვირთვის უდანაკარგო ტაბულური დატკეპნა სვეტურ `[N rows]` ფორმაში.                                                            |
| იონიზატორი      | `ionizer`       | Head/middle/tail მწკრივის ნიმუშის აღება ძალიან დიდი ჰომოგენური ბლოკებისთვის, მოხსნილი შუა ნაწილის შენახვა, როგორც CCR შინაარსის მისამართის მითითება.                          |
| სხდომა-შეწყვეტა | `session-dedup` | კონტენტის მიმართული ჯვარედინი შემობრუნების დედუპლიკაცია (TokenMizer-ის შთაგონებული): ელიდების ტექსტი, რომელიც უკვე ჩანს იმავე სესიის უფრო ადრეულ მონაცვლეობაში.               |

**CCR აღდგენის პროტოკოლის ინსტრუქცია (#8033):** პირველად, როდესაც CCR ანაცვლებს ≥ 1 ბლოკს მოთხოვნაში, ძრავა აგზავნის ერთ, უძლურ `system` შეტყობინებას (მიმდინარეობს `[CCR protocol]` Sentinel) ასწავლის აბონენტს მარკერის → ხელსაწყოს კონტრაქტს: რას ნიშნავს `[CCR retrieve hash=<24hex> chars=N]` მარკერი, რომ ჰეში უნდა დაკოპირდეს სიტყვასიტყვით (ყველა 24 თექვსმეტობითი სიმბოლო — შეცდომის გამოტოვება და სავარაუდოდ არ არის გამოტოვებული" `[dedup:ref sha=...]` მარკერი ნიშნავს "ისტორიაში გადახედვას" და არა "ინსტრუმენტს დარეკვას". შენიშვნა შეყვანილია** მხოლოდ მაშინ, როდესაც აბონენტის მიერ რეკლამირებული `tools[]` დაადასტურებს, რომ მას შეუძლია რეალურად მიაღწიოს `omniroute_ccr_retrieve`** (`callerSupportsCcrRetrieve()` in `open-sse/services/compression/engines/ccr/protocolInstruction.ts`) — უბრალო OpenAI-თან თავსებადი აბონენტი ამ ხელსაწყოს გარეშე არასოდეს იღებს ინსტრუქციას დარეკოს ის, რასაც ვერ აღწევს. იდემპოტენცია ძლიერდება შეტყობინებების ისტორიის სკანირებით სენტინელისთვის ინექციის დაწყებამდე, ასე რომ, მრავალჯერადი მოთხოვნის მოთხოვნა (რომლებიც იმეორებენ წინა შეტყობინებებს) არ აწყობენ შენიშვნას ყოველ ჯერზე ერთხელ.

## Caveman

Caveman რეჟიმი ფოკუსირებულია ნორმალური პროზის სემანტიკურ კონდენსაციაზე:

- ინახავს კოდის ბლოკებს, URLs, JSON, ბილიკებს და სტრუქტურირებულ მონაცემებს
- ხსნის შემავსებელს, ჰეჯირებას, განმეორებით კონტექსტს და სიტყვიერ შემაერთებელ ფრაზირებას
- მხარს უჭერს ენის მცოდნე ფაილის წესების პაკეტებს `open-sse/services/compression/rules/` ში
- ხელმისაწვდომი რჩება მოძველებული `standard`, `aggressive` და `ultra` რეჟიმების მეშვეობით

დაფის ზედაპირი არის `Dashboard -> Context & Cache -> Caveman`.

Caveman upstream იტყობინება `~75%` ნაკლები გამომავალი ჟეტონები, `65%` საშუალო გამომავალი დანაზოგი ბენჩმარკებში `22-87%` დიაპაზონით და `~46%` შეყვანის შეკუმშვის ხელსაწყო. OmniRoute იყენებს Caveman-ის შეყვანის გვერდის ნომერს დაწყობილი prompt/context დანაზოგების დოკუმენტირებისას; Caveman გამომავალი რეჟიმი რჩება ცალკე რეაგირება-ქცევის ფუნქცია.

## RTK

RTK რეჟიმი ფოკუსირებულია ბრძანებაზე და ხელსაწყოს გამომუშავებაზე:

- ამოიცნობს გამომავალი კლასებს, როგორიცაა `git status`, `git branch`, `git diff`, Vitest/Jest/Pytest, Cargo/Go ტესტები, TypeScript/Vite/Webpack builds, ESLint, npm audit/installs, Docker logs, shell `find`/`grep`, stack traces და ზოგადი ჟურნალები
- იყენებს 49 JSON ფილტრს `open-sse/services/compression/engines/rtk/filters/` დან
- მხარს უჭერს RTK-ის სტილის დეკლარაციულ მილსადენს: ANSI ამოღება, ჩანაცვლება, გამომავალი მოკლე ჩართვა, strip/keep ხაზები, თითო ხაზის შეკვეცა, head/tail/max-line შეკვეცა და ცარიელზე დაბრუნება
- მხარს უჭერს ნდობით დახურულ პროექტის ფილტრებს `.rtk/filters.json` ში და გლობალურ ფილტრებს `DATA_DIR/rtk/filters.json` ში
- აშორებს ANSI თანმიმდევრობებს, პროგრესის ხმაურს, განმეორებით ხაზებს და უსარგებლო ქვაბის ფირფიტას
- ინახავს სამოქმედო წარუმატებლობებს, გაფრთხილებებს, შეჯამებებს, შეცვლილ ფაილებს და კუდის კონტექსტს
- შეუძლია სურვილისამებრ შეინარჩუნოს დამუშავებული ნედლეულის გამომავალი recovery/debugging სთვის ავტორიზებული მართვის მარშრუტების მეშვეობით

დაფის ზედაპირი არის `Dashboard -> Context & Cache -> RTK`.

საოპერაციო დეტალები მორგებული ფილტრების, ნდობის, გადამოწმებისა და ნედლეულის აღდგენისთვის ცოცხალია [`RTK_COMPRESSION.md`](./RTK_COMPRESSION.md) ში.

RTK upstream აცნობებს `60-90%` დანაზოგს ბრძანება-გამომავალი შეკუმშვისთვის. მისი README მაგალითი გვიჩვენებს 30-წუთიან Claude Code სესიას, რომელიც გადადის `~118,000` ტოკენებიდან `~23,900` ზე, ან `79.7%` შენახულზე.

## LLMLingua-2 (სემანტიკური მორთვა)

LLMLingua-2 რეჟიმი ასრულებს** სემანტიკური ნიშნის გასხვლა** პროზაზე მცირე ONNX ნიშნის კლასიფიკატორის გამოყენებით, რომელიც ავსებს წესებზე დაფუძნებულ Caveman და RTK ძრავებს:

- შეკუმშავს პროზას მხოლოდ არასისტემურ შეტყობინებებში; შემოღობილი კოდის ბლოკები და სხვა შემონახული კონსტრუქციები არასოდეს იცვლება
- აწარმოებს `@atjsh/llmlingua-2` backend-ს (ONNX via `@huggingface/transformers`) მუშა თემაში, ამიტომ მოდელის დასკვნა არასოდეს დაბლოკავს მოთხოვნის მოვლენის ციკლს
- არის** დაწყობადი** (`stackPriority` 35): დაწყობილ მილსადენში ის გადის სტრუქტურული ძრავების (CCR, session-dedup, headroom, Caveman) შემდეგ, მაგრამ `ultra` მდე, რადგან სემანტიკური მორთვა ყველაზე ეფექტურია უკვე სტრუქტურულად შეკუმშულ ტექსტზე — მაგ. `rtk -> caveman -> llmlingua`
- **fail - იხსნება ნებისმიერი შეცდომის დროს** (აკლდება არასავალდებულო ჩაღრმავები, მუშა ქვირითი, მოდელის ჩატვირთვა, დასკვნა ან დროის ამოწურვა) → თავდაპირველი ტექსტი ბრუნდება უცვლელი, არასოდეს არის შეცდომა

ძრავის ადგილმდებარეობა: `open-sse/services/compression/engines/llmlingua/`. დაფის ზედაპირი არის `Dashboard -> Context & Cache -> LLMLingua`.

### მოდელები

ნაგულისხმევი მოდელი არის**TinyBERT** (`atjsh/llmlingua-2-js-tinybert-meetingbank`, ~ 57 MB, სწრაფი). უფრო მაღალი სიზუსტით** BERT-ბაზა** მოდელი (`Arcoldd/llmlingua4j-bert-base-onnx`, ~ 710 MB) ხელმისაწვდომია ძრავის კონფიგურაციის `model` ველში. `@huggingface/transformers` ზარმაცად ჩამოტვირთავს არჩეულ მოდელს HuggingFace Hub-დან `${DATA_DIR}/models/llmlingua` ში პირველი ზარის დროს (`modelStore.ts`); ამის ნაცვლად, `modelPath` კონფიგურაციის უგულებელყოფა მიუთითებს ლოკალურ ასლზე (ხაზგარეშე/ჰაერ-გაფართოვებული ინსტალაციები).

### სურვილისამებრ დამოკიდებულებები და მოთხოვნით ინსტალაცია

prunable LLMLingua runtime peer stack არის** სურვილისამებრ** . ორი პაკეტი გამოცხადებულია `optionalDependencies` ად `package.json` ში და ინახება** გარე** წარმოების კონსტრუქციით (`scripts/build/prepublish.ts` არ აერთიანებს მათ):

| პაკეტი               | ვერსია (პინი) | შენიშვნები                                       |
| -------------------- | ------------- | ------------------------------------------------ |
| `@atjsh/llmlingua-2` | `2.0.5`       | შესვლის პაკეტი; დანარჩენებს თანატოლებად აცხადებს |
| `js-tiktoken`        | `^1.0.20`     | ტოკენიზატორი                                     |

`@huggingface/transformers` არის მიმაგრებული `^4.2.0` ზე (გაზიარებულია ლოკალური ჩაშენების გზასთან და ასევე იკვეთება ცალკეულ პაკეტში); `@atjsh/llmlingua-2@2.0.5` მასზე უერთდება `"^3.5.2 || ^4.0.0"`, ამიტომ ორივე Transformers.js v3 და v4 მხარდაჭერილია. 2.0.4-დან `@atjsh/llmlingua-2` აღარ საჭიროებს `@tensorflow/tfjs`, რამაც ამოიღო ყველაზე დიდი ერთი კონტრიბუტორი (TensorFlow.js) SLM სტეკიდან. მხოლოდ ზემოთ მოყვანილი ორი პაკეტი არის prunable SLM თანატოლები. სტანდარტული `npm install` (dev) ავტომატურად აყენებს არჩევით დასტას, თუ არჩევითი დამოკიდებულებები არ არის გამოტოვებული.

**რატომ მოთხოვნით:** npm-ის გამოქვეყნებული პაკეტი, დამოუკიდებელი პაკეტი და Docker გამოსახულების გემი** გარეშე** ეს ღეროები გამხდარი დარჩენისთვის. როდესაც ისინი არ არიან, მუშაკის დამოკიდებულების კარი ( `@atjsh/llmlingua-2` გადაწყვეტის ზონდი `worker.ts` ში) იშლება და ძრავა** fail-იხსნება ჩუმად** — შერჩევისას LLMLingua ხდება no-op (ტექსტი დაბრუნდა უცვლელი, შეცდომა არ არის შესული). გასხვილ გარემოში მის გასააქტიურებლად დააინსტალირეთ არჩევითი დასტა:

```bash
# pin to the versions declared in package.json optionalDependencies
npm install @atjsh/llmlingua-2@2.0.5 js-tiktoken
```

`@tensorflow/tfjs` ამოღება (2.0.4 +) გამორიცხავს ადრე დომინანტურ ~ 800 MB კონტრიბუტორს — დარჩენილი კვალი არის transformers.js + onnxruntime-node გაშვების დროები, პლუს TinyBERT მოდელი (~ 57 MB), რომელიც ჩამოტვირთულია პირველი გამოყენებისას (არა npm-ით).

გარემოს მიხედვით:

- **Dev / `npm install`** — დაინსტალირებულია ავტომატურად, თუ არ ჩააბარეთ `--omit=optional` (ან `--no-optional`). არანაირი ქმედება არ არის საჭირო.

- **Docker** — დაამატეთ ინსტალაციის ბრძანება მიღებული გამოსახულების ფენაში; გამოქვეყნებული სურათი დიზაინით თხელია.
- **VPS (PM2)** — დააინსტალირეთ აპლიკაციის `node_modules` ში, შემდეგ გადატვირთეთ პროცესი, რათა მუშაკი ხელახლა გამოიძიოს კარიბჭე.
- **Raw შემდეგი დამოუკიდებელი (`npm run build` → `.build/next/standalone/server.js`)** — დამოუკიდებელი კვალი გემების NEITHER მუშაკი ან სურვილისამებრ ჩაღრმავები, ასე რომ ძრავა ჩუმად იხსნება. `scripts/build/colocate-standalone.mjs` ხელახლა იყენებს ორივეს (მუშაკი esbuild + სურვილისამებრ-ღრმა დახურვა ცალკეულ ხეში); ის ავტომატურად მუშაობს `postbuild` npm hook-ის მეშვეობით ყოველი აშენების შემდეგ. იდემპოტენტური, მარცხი-რბილი, როდესაც სიღრმეები არ არის.

**დარწმუნდით, რომ ის აქტიურია:** LLMLingua შერჩევით, რეალური პროზა ფაქტობრივად იკუმშება (ძრავა წყვეტს გაუმართაობის გახსნას) და პირველი მოთხოვნა იწვევს მოდელის ჩამოტვირთვა `${DATA_DIR}/models/llmlingua` ში. კარიბჭე განზრახ იკვლევს მხოლოდ `@atjsh/llmlingua-2` — სხვა თანატოლები მხოლოდ ESM-ზეა და `require.resolve` ისვრის მათ მაშინაც კი, როდესაც არსებობს — ასე რომ მუშაკი მაინც ვერ იხსნება, თუ რომელიმე თანატოლი ნამდვილად აკლია `import()` დროს.

## დაწყობილი მილსადენები

დაწყობილი რეჟიმი მილსადენის საფეხურებს თანმიმდევრობით ატარებს. ნაგულისხმევი არის:

```txt
rtk -> caveman
```

გამოიყენეთ ეს კოდირების აგენტის სესიებისთვის, სადაც სწრაფი ბრძანება აერთიანებს ადამიანურ ან დამხმარე პროზას. RTK ჯერ ამცირებს ხმაურიანი ხელსაწყოების ჟურნალებს, შემდეგ Caveman შეკუმშავს დარჩენილ ბუნებრივ ენას.

მილსადენის საფეხურები კონფიგურირებულია `stackedPipeline` ით შეკუმშვის პარამეტრებში ან შეკუმშვის კომბინაციების საშუალებით.

როდესაც ორივე ძრავა ამცირებს ერთსა და იმავე უფლებამოსილ დატვირთვას, შემნახველი ნაერთი:

```txt
combined = 1 - (1 - RTK savings) * (1 - Caveman input savings)
average  = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
range    = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4-94.6%
```

## MCP ხელმისაწვდომობის ხის ფილტრი

MCP accessibility-tree smart filter არის შესრულების შემდგომი შეკუმშვის ფენა, რომელიც მუშაობს MCP ზე** ხელსაწყოს შედეგები** , არა მოთხოვნაზე ან კონტექსტზე. ის მიზნად ისახავს ვრცელი ხელმისაწვდომობის ხეს და ბრაუზერის სნეპშოტის დატვირთვას, რომელიც დაბრუნებულია ისეთი ინსტრუმენტებით, როგორიცაა Playwright, კომპიუტერის გამოყენება და ბრაუზერის ავტომატიზაციის MCP სერვერები.

### რასაც აკეთებს

1. **ხმაურის ამოღება** — შლის generic/text ცარიელ ჩანაწერებს (`- generic:`, `- text: ""`)
2. **და-ძმის კოლაფსი** — როდესაც ≥ `collapseThreshold` (ნაგულისხმევი 30) თანმიმდევრული ხაზები სტრუქტურული გამეორებაა, ანაწილებს მათ პირველ `collapseKeepHead` (ნაგულისხმევი 10) ხაზებად + რიცხვის შეჯამება + ბოლო `collapseKeepTail` (ნაგულისხმევი 5) ხაზებად
3. **Ref შენარჩუნება** Playwright/computer-use მიერ მოთხოვნილი — `[ref=eXX]` წამყვანები არასოდეს შეხებიან
4. **მძიმე შეკვეცა** — თუ ტექსტი კოლაფსის შემდეგ კვლავ აღემატება `maxTextChars` (ნაგულისხმევი 50000), იჭრება ნავიგაციის მინიშნებით, რათა აგენტმა გააგრძელოს მუშაობა

### ძრავის მდებარეობა

```txt
open-sse/services/compression/engines/mcpAccessibility/
  index.ts            ← smartFilterText() entry point
  collapseRepeated.ts ← sibling-collapse algorithm
  constants.ts        ← DEFAULT_MCP_ACCESSIBILITY_CONFIG
```

### კონფიგურაცია

აკონტროლებს `compression.mcpAccessibility` გლობალურ პარამეტრებში (მიგრაცია 056). ნაგულისხმევი კონფიგურაცია:

```json
{
  "enabled": true,
  "maxTextChars": 50000,
  "collapseThreshold": 30,
  "collapseKeepHead": 10,
  "collapseKeepTail": 5,
  "minLengthToProcess": 2000
}
```

ფილტრი გამოიყენება მხოლოდ ხელსაწყოების შედეგიან დატვირთვებზე, რომელთა `type` არის `"text"` და რომლის სიგრძე აღემატება `minLengthToProcess`. ეს არ იმოქმედებს სწრაფ შეკუმშვაზე ან დატვირთვის მოთხოვნაზე.

### მოსალოდნელი დანაზოგი

60–80% ბრაუზერის Snapshot ინსტრუმენტის შედეგებზე, გვერდის სირთულის მიხედვით. კოლაფსის ალგორითმი არის O(n) ხაზების რაოდენობაში და ამატებს უმნიშვნელო შეყოვნებას.

## წინაპირობები / ოპერატორის სახელმძღვანელო (CCR & session-dedup)

CCR (`ccr`) და `session-dedup` შეცვალეთ ან აარიდეთ ტექსტი და დატოვეთ a** მარკერი** უკან. ეს განყოფილება არის ოპერატორის მითითება კლიენტის გაყვანილობისთვის, ორი მარკერის წაკითხვისთვის და ამოღებული შინაარსის მისაღებად ან დიაგნოსტირებისთვის. ზემოთ მოცემულია თითოეული ძრავის მექანიკა; ეს არის "როგორ გავუშვა" ფენა.

### ტრანსპორტი და ბოლო წერტილები

MCP სერვერზე, რომელიც ავლენს CCR ინსტრუმენტებს, შეგიძლიათ მიაღწიოთ სამი გზით. ნაგულისხმევი ბაზა URL არის `http://localhost:20128` (`OMNIROUTE_BASE_URL`):

| ტრანსპორტი                                  | URL / ბრძანება                          | შენიშვნები                                                                                                                                      |
| ------------------------------------------- | --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| სტრიმირებადი HTTP (კლიენტი, რეკომენდებულია) | `http://localhost:20128/api/mcp/stream` | საბოლოო წერტილის ამჟამინდელი MCP კლიენტები საუბრობენ.                                                                                           |
| Legacy SSE singleton                        | `http://localhost:20128/api/mcp/sse`    | ძველი სინგლის ტრანსპორტი. ის** იხურება** სტრიმინირებადი სესიები; გამოიყენეთ `streamable-http` კლიენტები `/api/mcp/stream` წინააღმდეგ და არა ეს. |
| stdio                                       | `omniroute --mcp`                       | IDE MCP კონფიგურაციისთვის, რომელიც წარმოშობს პროცესს. არ არსებობს `--dev` დროშა; `omniroute --mcp` არის stdio შესასვლელი წერტილი.               |

### შენახვის დონეები (რაც გადარჩება გადატვირთვას)

CCR არის ა** ორსართულიანი** შენახვა, არა მხოლოდ მეხსიერებაში:

- **ცხელი მეხსიერების დონე** — ბლოკის ქუდი 2 MiB, თითო პრინციპი 16 MiB, გლობალური 64 MiB. ჩანაწერები ნაგულისხმევად არის 24 სთ TTL (მაქსიმუმ 7 დღე). სრული MCP ამოღება მეხსიერებიდან შემოიფარგლება 256 KiB; ნებისმიერი უფრო დიდი ჯერ კიდევ ხელმისაწვდომია დიაპაზონის / grep რეჟიმების საშუალებით.
- **გამძლე SQLite იარუსი** (`ccr_blocks`, `COMPRESSION_CCR_DURABLE_STORE`, ჩართული ნაგულისხმევად) — მხარს უჭერს მეხსიერების დონეს, ასე რომ, ბლოკი გადარჩება LRU გამოდევნას, გადატვირთვას ან სხვა ინსტანციაზე დაშვების აღდგენას. მწკრივი ინარჩუნებს ბლოკის TTL ს, ამიტომ ბლოკი, რომელიც მის TTL გასცდება, ორივე იარუსიდან გაქრება.

სამი მცველი ინარჩუნებს გამძლე იარუსს შემოსაზღვრულ — და ბლოკი რჩება მეხსიერებაში მხოლოდ მაშინ, როდესაც:

1. ბლოკი დასრულდა** 512 KB** (`MAX_DURABLE_BLOCK_BYTES`);
2. გაშვების დრო არის ღრუბლოვანი სამუშაო დრო (ლოკალური დისკის გარეშე);
3. `COMPRESSION_CCR_DURABLE_STORE=false`.

ასე რომ, „ბლოკი გაქრა“ არ არის სრული გადატვირთვის ამბავი: sub-512 KB ბლოკი ლოკალურ, ღრუბელ არაღრუბელზე გაშვებულ დროზე გადარჩება გადატვირთვისას გამძლე დონის მეშვეობით, სანამ მისი TTL ამოიწურება. იხილეთ [გარემოს მითითება](../reference/ENVIRONMENT.md) ცვლადისთვის.

### ორი მარკერი

| მარკერი                               | მნიშვნელობა                                                                                                                                 | რა უნდა გააკეთოს მოდელმა                                                                                                                                                                                                   |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `[CCR retrieve hash=<24hex> chars=N]` | დიდი ბლოკი ინახებოდა კონტენტის მისამართით.                                                                                                  | დარეკეთ `omniroute_ccr_retrieve` სთან ერთად** 24-თექვსმეტიანი ჰეში დაკოპირებულია სიტყვასიტყვით** ორიგინალური ტექსტის დასაბრუნებლად.                                                                                        |
| `[dedup:ref sha=…]`                   | `session-dedup` elided ტექსტი უკვე გაიგზავნა იმავე სესიის უფრო ადრეულ ეტაპზე. ეს არის** განზრახ უკან დაბრუნება** , არა დაკარგვა ან შეცდომა. | გააკეთე** არა** დაურეკეთ ნებისმიერ ხელსაწყოს და გააკეთეთ** არა** სცადეთ მისი "რეკონსტრუქცია". ტექსტის პირველი შემთხვევა არის კანონიკური ასლი; მიმდინარე ბრუნი არასოდეს გადაიწერება, ის წაშლილია მოგვიანებით შემობრუნებაზე. |

`[dedup:ref]` უკან დაბრუნება არის მიზანმიმართული პროტოკოლის გადაწყვეტილება — არ არის წინასწარ გაგზავნილი რეკონსტრუქცია. მოექეცით მას, როგორც "ეს ზუსტი ტექსტი უკვე იყო სადენზე ადრე ამ სესიაზე."

### კლიენტის წინაპირობები

- **გასაღები (stdio):** stdio აბონენტს არ აქვს თითო მოთხოვნის იდენტიფიკაცია, ამიტომ იგი ავთენტიფიცირებულია `OMNIROUTE_API_KEY` ით (დაყენებულია MCP სერვერის `env`). ამის გარეშე აბონენტი ანონიმურია და ინსტრუმენტები, რომლებიც საჭიროებენ მთავარს, შეიძლება დაქვეითდეს.
- **`tools[]` არის ინექციის წინაპირობა.** შეყვანილია CCR აღდგენის პროტოკოლის ინსტრუქცია (#8033).** მხოლოდ** როდესაც მოთხოვნის რეკლამირებული `tools[]` ამტკიცებს, რომ კლიენტს შეუძლია რეალურად მიაღწიოს `omniroute_ccr_retrieve`. დამთხვევა არის ბოლო სეგმენტის შესატყვისი, რომელიც შემოიფარგლება გამყოფით (`__`, `.`, `/`, `:`) — არასოდეს არის შიშველი ქვესტრიქონი —, ამიტომ სახელთა სივრცის სახელი, როგორიცაა `mcp__gateway__omniroute_ccr_retrieve` კვლავ ითვლის. არარსებული ან შეუსაბამო `tools[]` ნიშნავს, რომ ინსტრუქცია _არ არის შეყვანილი დიზაინის მიხედვით.
- **`codemode:false` (OpenCode კლიენტები).** OpenCode ნაგულისხმევად არის კოდის რეჟიმი, რომელიც რეკლამირებს მხოლოდ მის მშობლიურ ინსტრუმენტებს მოდელზე და** არ აკეთებს** დააყენეთ MCP ინსტრუმენტები მშობლიურ `tools[]` სიაში. დააყენეთ `codemode: false` MCP სერვერის ჩანაწერზე, რათა `omniroute_ccr_*` ინსტრუმენტები იყოს რეკლამირებული. ეს არის ა** კლიენტი** პარამეტრი, არა OmniRoute ერთი. ის ჯერ არ იღებს CCR ინსტრუქციას: OpenCode ასახელებს ინსტრუმენტს `<server>_<tool>`, ამიტომ სერვერი, სახელად `omniroute` ავლენს `omniroute_omniroute_ccr_retrieve` და `_` არ არის ერთ-ერთი შესაბამისი გამყოფი.
- **დირექტორები.** შენახვა და მიღება იზოლირებულია ავტორიზებული პრინციპის მიხედვით (თითო API გასაღები). გასაღები ხედავს მხოლოდ საკუთარ ბლოკებს.

### მოძიების ლიმიტები და პაგინაცია

MCP ინსტრუმენტის ტექსტის შედეგები მოჭრილია `mcpAccessibility.maxTextChars` გარშემო (ნაგულისხმევი `50000`). ბლოკის `full` აკრეფა არის 256 KiB —** არ არის შეუზღუდავი სრული მოძიება** . როდესაც ბლოკის `chars=N` დიდია, გვერდი აიღეთ, ნაცვლად იმისა, რომ აიღოთ ყველაფერი:

- ცერის წესი:**`chars > 40000` → გამოიყენეთ `mode`** , არასოდეს შიშველი სრული.
- `mode:"grep"` — regex `pattern` შეესაბამება სტრიქონს, 1000-მდე შესატყვისი ხაზი (`unique: true` წვეთები მეორდება), ყველაზე იაფი "იპოვე ერთი ხაზი, რომელიც მჭირდება."
- `mode:"lines"` — 1-ინდექსირებული ხაზის დიაპაზონი; სჭირდება როგორც `start`, ასევე `end`.
- `mode:"head"` / `mode:"tail"` — first/last `n` ხაზები.
- `mode:"stats"` — ხაზი, სიმბოლო და ბაიტი ითვლის სხეულის გარეშე.

გამოიყენეთ `mode:"lines"` `start`/`end` ით, რათა გაიაროთ გრძელი ბლოკი გვერდებზე, ვიდრე მოითხოვოთ ყველაფერი ერთდროულად.

### ხელსაწყოს დასახელება

აღდგენის ხელსაწყოს ამჟამად ჰქვია `omniroute_ccr_retrieve` ( `omniroute_` პრეფიქსი არის დათარიღებული გამოსავალი ჯვარედინი სერვერის სახელების შეჯახებისთვის). სუფთა შემოსაზღვრული სუფიქსის ხელსაწყოს სახელი და შესწორება MCP JSON შედეგების შეკვეცილი შუა სტრიქონი თვალყურს ადევნებენ, როგორც ზედა დინების შემდგომი მოქმედებები; ეს გვერდი ადასტურებს მხოლოდ მიმდინარე, გაგზავნილ ქცევას.

### სესიის სასიცოცხლო ციკლი

Streamable-HTTP სესიები გამორთულია და სერვერი იღებს მათ; უმოქმედო ფანჯარა არის `MCP_SESSION_IDLE_MS` მუდმივი (მითითებულია სახელით და არა მყარი კოდირებული მნიშვნელობით, ასე რომ, ეს გვერდი არ დრიფტირდება, როდესაც იცვლება). უსაქმური სესიის სიმპტომია HTTP 404 `Unknown Mcp-Session-Id` — ით, გამოსავალი არის სესიის ხელახლა დაკავშირება ან გადატვირთვა,** არა** გასაღების დასატრიალებლად, ფარგლების შესაცვლელად ან ხელსაწყოს სახელის გადარქმევა.

## ფარგლები და გამონაკლისები

**ჩაშენებები არასოდეს არის შეკუმშული.** `open-sse/handlers/embeddings.ts` არასოდეს უწოდებს რაიმე შეკუმშვის ძრავას — request/response სხეულები პირდაპირ შემსრულებელს ხელუხლებლად გადადიან. ეს დღეს სტრუქტურულია (ჩაშენებები და ჩეთის დასრულებები არაერთგვაროვანი დამმუშავებლებია), არა გაშვების დროის შემოწმება, მაგრამ ეს ნიშნავს, რომ #8034 ში ვექტორული დამახინჯების პრობლემა არ აქვს ექსპოზიციის ზედაპირი ჩაშენების გზაზე.

**Per-model/endpoint გამორიცხვის ფილტრი (#8034).** ჩეთის დასრულებისთვის, ოპერატორს შეუძლია დაასახელოს მოდელის id/ `provider/model` სამიზნეები, რომლებიც არასოდეს უნდა იყოს შეკუმშული — დამცავი რგოლისთვის, სასარგებლოა, თუ შეკუმშვა მოგვიანებით იქნება მიბმული ჩაშენების მიმდებარე ბილიკთან და ზოგადად გამოსადეგია ნებისმიერი მოდელისთვის, რომლის ზუსტი ბაიტი-ბაიტი მოთხოვნადია (განმსაზღვრელი ევალები, წინასწარი ქეშები და ა.შ.).

- პარამეტრების ველი: `exclusions?: string[]` გლობალური შეკუმშვის კონფიგურაციაზე (`GET`/`PUT /api/settings/compression`), შენარჩუნებულია არსებული `key_value` შეკუმშვის სახელთა სივრცის მეშვეობით (`src/lib/db/compression.ts`) — ახალი ცხრილის გარეშე.
- დაფის ჩანართი:** დაფა → შეკუმშვის → გამონაკლისები** (`/dashboard/compression/exclusions`).
- ნიმუშის სინტაქსი: `*` ერთადერთი სიმბოლოა. შაბლონში ყველა სხვა რეგექსის მეტანიშანი გაურბის დამთხვევამდე, ამიტომ `gpt-5.6` ემთხვევა მხოლოდ ლიტერალურ სტრიქონს, არასდროს `gpt-5x6` (ReDoS-უსაფრთხო, შემოსაზღვრული, წყობილი რაოდენობების გარეშე). შაბლონები შეუსაბამოდ ემთხვევა როგორც შიშველი მოდელის id-ს, ასევე `provider/model` კომპოზიტს — `gpt-5-6`, `openai/gpt-5-6` და `openai/*` ყველა მუშაობს და მხოლოდ `*` გამორიცხავს ყველა მოდელს.
- შესატყვისი: `isCompressionExcluded()` / `normalizeCompressionExclusions()` `open-sse/services/compression/exclusions.ts` ში. `chatCore.ts` ამოწმებს გამორიცხულ სამიზნეს შეკუმშვის პარამეტრების გადაჭრისთანავე,** სანამ რომელიმე ძრავა მუშაობს** , და ეპყრობა შესაბამისობას ზუსტად ისე, როგორც შეკუმშვა, რომელიც გლობალურად გამორთულია — მოთხოვნის სხეული აშკარად ბაიტის იდენტურია. გამოტოვება ჩაწერილია `writeCompressionSkip(..., "excluded")` საშუალებით ანალიტიკის ხილვადობისთვის.
- ნაგულისხმევი (empty/absent სია): იდენტურია pre-#8034 ქცევა — არაფერია გამორიცხული.
